# Phase 04.1: Exam Creation Enhancements & Evaluation Settings - Research

## Standard Stack
- **Laravel Migrations**: Standard `Schema::table` approach to add fields to `exams` and `exam_attempts` tables.
- **Inertia.js + React**: Frontend form handling, state management, and tabbed UI for both the Admin Exam Builder and the Student Exam View.
- **Radix UI**: The standard component library used in this project. Specifically, `@radix-ui/react-tabs` should be utilized for all tabbed interfaces to ensure accessibility and consistent styling.
- **Laravel Wayfinder**: Use Wayfinder for strongly typed routing when calling backend endpoints (e.g., submitting individual sections, announcing results).

## Architecture Patterns
- **Incremental Schema Updates**: Create new migration files rather than modifying existing ones (since previous phases are complete). 
  - `exams` table needs: `class_name`, `subject_name`, `evaluation_strategy` (enum/string: e.g., 'instant', 'manual'), and `results_announced_at` (timestamp or boolean).
  - `exam_attempts` table needs tracking for individual section submissions: `tf_submitted_at`, `mcqs_submitted_at`, `written_submitted_at`.
- **Tabbed Exam UI (Admin)**: The admin exam builder should encapsulate the creation/editing of True/False, Multiple Choice, and Written questions into separate tab panes. The main exam details (class, subject) should remain visible or be part of a primary settings pane.
- **Sectional Submission (Student)**: The student exam interface must allow submitting one tab (e.g., TF) independently of others. This requires separate form submissions or API endpoints per section, returning an updated state that locks the submitted tab.
- **Result Announcement Pipeline**: Instead of grades being instantly visible (if configured as manual), the results view logic must check `results_announced_at`. Admins need a dedicated action/button on the exam management page to set this timestamp, revealing results to students.

## Don't Hand-Roll
- **Tab Components**: Do not build custom state-based tab switchers using raw `div`s and `onClick` handlers. Use the existing `@radix-ui/react-tabs` components.
- **Validation Constraints**: Do not rely on frontend-only locking for submitted sections. The backend controller must strictly verify `if ($attempt->tf_submitted_at) abort(403);` to prevent tampering.

## Common Pitfalls
- **Breaking Existing Exams**: Ensure new database columns are `nullable()` or have sensible `default()` values so exams created in Phase 2 do not break.
- **Lost State on Section Submit**: When a student submits one section (e.g., MCQs), the Inertia response must preserve their unsubmitted answers in other sections, or the frontend must handle the submission via a partial reload/API call to avoid wiping local React state.
- **Inconsistent Evaluation Visibility**: The logic defining whether a student can see their result involves checking both the exam's `evaluation_strategy` and whether `results_announced_at` is set. This logic should ideally be encapsulated in a model accessor or a dedicated service class rather than duplicated in views.

## Code Examples

**Migration Example:**
```php
Schema::table('exams', function (Blueprint $table) {
    $table->string('class_name')->nullable();
    $table->string('subject_name')->nullable();
    $table->enum('evaluation_strategy', ['instant', 'manual'])->default('instant');
    $table->timestamp('results_announced_at')->nullable();
});
```

**Section Submission Verification Example:**
```php
public function submitSection(Request $request, ExamAttempt $attempt) {
    $section = $request->input('section'); // 'tf', 'mcqs', 'written'
    
    if ($attempt->{"{$section}_submitted_at"}) {
        return back()->withErrors(['message' => 'This section has already been submitted.']);
    }
    
    // Process answers...
    
    $attempt->update(["{$section}_submitted_at" => now()]);
    
    return back();
}
```
